# Register port: recorded divergences

Reference: `ukiryu/ukiryu` at `ab6df353c6dc2d7faf7817a86aafcafa82579896`,
`lib/ukiryu/register.rb`. `reference.json` is regenerated by running
`ruby fixtures/register/capture-reference.rb <ruby-reference>` (git gem 4.3.1
when captured). `spec/` is a verbatim copy of `spec/fixtures/register`; the
script refuses to run if the copy differs.

## Safety divergence (source hazard)

- **Clone failure deletes the target directory.** `Register#clone!` runs
  `FileUtils.rm_rf(path) if Dir.exist?(path)` on any `Git::Error`. When the
  target already exists with content but no valid register structure (for
  example `ensure_exists!` on a populated `~/.ukiryu/register`), git refuses
  to clone into it and the source then deletes the user's directory. The
  oracle demonstrates this (`clone.occupied_survives: false`). The port only
  removes a directory that did not exist before the clone attempt; a
  pre-existing directory is never deleted. The test asserts both facts.

## Behaviour divergences

- `Register.exists?` returns `nil` (not `false`) when no path resolves; the
  port returns `bool` (`false`).
- `update!` on a directory outside a git working tree: the git gem raises
  `ArgumentError` ("'<path>' is not in a git working tree"), which the source's
  `rescue Git::Error` does not catch. The port preserves the class name and
  message as `Error::NotGitWorkTree`.
- Clone failure text: the source embeds the git gem's `Git::FailedError`
  message (Ruby inspect of the full command, environment and stderr). The port
  embeds `git <args> failed with <status>: <stderr>` from the installed git.
  The Ukiryu framing (first-line prefix, the "To fix this" guidance and its
  `git`-not-in-PATH classification) is identical and tested.
- Progress output (`Cloning register from ...`, `done`, `Updating
  register...`) is printed by the source when stdout is a TTY. The shared core
  does not print; adapters own presentation.
- `update!` sets `ENV['GIT_REDIRECT_STDERR']` process-wide during the pull.
  The port never mutates process environment; git's stderr is captured.
- `discover_path` without a home directory: `File.expand_path('~')` raises
  `ArgumentError` in the source. The port returns `None` from
  `discover_path` and `NotFoundError` from `discover`.
- The development register path is derived by the source from its own file
  location (`<gem root>/register`). The port takes it as explicit
  `DiscoveryContext::dev_path` input; the oracle injects the same values.
- `Register.at` uses a lexical expansion (absolute path, `.`/`..` folded) and
  does not expand `~`.
- `list_versions` returns `VersionFile { path, equals }` with the YAML
  `equals` value (string/integer/float preserved, as captured) instead of a
  Ruby Hash keyed by path string. Ordering and duplicate handling (first
  position, last value) match the oracle.
- Index shapes the source cannot handle (non-mapping index, non-list
  `implementations`/`versions`, non-string `file`) raise `NoMethodError` /
  `TypeError` in Ruby; the port returns `Error::InvalidIndex` with the
  corresponding Ruby-style message.

## Not ported here (other owners / out of scope)

- Deprecated class shims that mutate `ENV` (`default_register_path=`) or the
  memoized `Register.default` singleton: runtimes hold their own `Register`.
- `load_tool_metadata` (ToolIndex / ToolMetadata) and `validate_tool` /
  `validate_all_tools` (SchemaValidator) belong to the routing and model
  owners.
- Typed model conversion (`Models::ImplementationIndex.from_hash` etc.): the
  load functions are generic over the model type; tests currently decode into
  the YAML tree. Model-level comparison (for example the `interface_version`
  default of `'1.0'`) is pending the shared model types.
